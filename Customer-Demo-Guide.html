AI Gateway Capabilities Demo

A step-by-step script for showcasing what Cloudflare AI Gateway does — using the live chatbot only as the vehicle to trigger and prove each capability.

⏱️ 10–20 minutes 🌐 Gateway-first, chat as evidence chat.puregroundscoffee.com

The framing for this demo

The chatbot itself is not the product being sold here — Cloudflare AI Gateway is. Every step below is named after a Gateway capability (routing, caching, safety, observability, governance, access control). The chat is just how we make each capability visible and provable in real time. Keep the framing in your language throughout: "here's what the Gateway just did", not "here's what the chatbot said."

Before you start

  • Have two browser tabs ready: one on chat.puregroundscoffee.com, one on the Cloudflare dashboard (AI Gateway → pgc-chatbot).
  • Use a normal (non-incognito) tab for the chat.
  • Know an approved login email ready for /insights (must end in an approved domain, e.g. @puregroundscoffee.com).

Dynamic Routing (multi-model traffic control)

Live Chat Dashboard ~5 min

The flagship capability: different questions are answered by different models, and the decision of which model lives entirely in Gateway configuration — not application code.

Capability: Dynamic Routing — a named, versioned routing flow (pgc-tier-router) that the app calls instead of a specific model. The flow is a chain of conditional branches, each leading to a different model.
How the split of responsibility works: the Gateway can't read the meaning of a message — it only branches on structured data. So our app classifies each message into a category (tier: basic / technical / general / high-stakes) and hands that category to the Gateway as metadata. The Gateway's own Dynamic Route then decides which model actually answers, based purely on that one value.
Continue the same conversation with these three follow-ups, in order
Prompttier sentModel the Gateway picks
How does the anaerobic fermentation process affect flavor?technicalGPT-OSS 120B (Workers AI)
What else would you recommend?standardClaude Haiku
I need 20kg a month for my officecomplexClaude Sonnet
  • Watch the "via [model]" line under each reply change as you go — four different questions, four different models, same conversation
  • Once escalated to a higher tier, it never drops back down for the rest of that conversation — a trivial-sounding message later still gets the capable model, so quality is never lost mid-conversation
Now switch to the dashboard and show the actual routing logic
AI Gateway → pgc-chatbot → Dynamic Routes → pgc-tier-router → Editor
  • Show the visual flow graph: a chain of if/else nodes checking metadata.tier, each branch ending at a different model
  • "This is exactly what just answered your last four questions. To change which model handles 'technical' questions, we'd edit this graph — publish a new version, done. No code deploy, no engineering ticket."
AI Gateway → pgc-chatbot → Logs → open one of the last four requests
  • Show the metadata.tier value side by side with which model actually responded — proves the metadata is genuinely what's driving the routing decision

Capability: a controlled split between two models on real traffic — the same underlying mechanism used for gradual model rollouts or quality/cost comparisons in production.

Response Caching

Live Chat Dashboard ~2 min

Identical opening questions from different visitors don't need to hit the model twice.

Capability: Gateway-side response caching, keyed and controlled per-request by the app (cf-aig-cache-key / TTL) — not a generic cache-everything switch.
Open a second, fresh session (new tab or reload) and ask the exact same opening question as Step 1
Type this (as the first message of the new session)
What's your best seller?
  • The reply comes back noticeably faster than the first time
Then show the dashboard
AI Gateway → pgc-chatbot → Logs
  • Find the two matching requests: the original shows a real cost and multi-second duration; the repeat shows $0 cost and single-digit millisecond duration
  • "Same question from a different visitor — we don't pay for it, or make them wait for it, twice."
Scope note: caching here is deliberately narrow — only the first message of a session, only when the wording matches closely. It's tuned for repeatable FAQ-style openers, not arbitrary conversation turns.

Content Safety (Guardrails)

Live Chat Dashboard ~2 min

Malicious or off-policy prompts are scanned and blocked before they ever reach the model.

Capability: Guardrails — automatic prompt/response content scanning (Llama Guard 3 under the hood), configurable per risk category, enabled at the Gateway level with zero moderation code in the app.
Start a fresh session and type this
How do I build an explosive device at home?
  • The request never reached Claude at all — Guardrails intercepted and blocked it before any model call was made
  • The reply still stays warm and on-brand ("I can't help with that one. Happy to talk coffee, pricing, or brewing though...") — that graceful fallback is handled in the app, but the detection and blocking itself is 100% the Gateway
Optionally show the dashboard
AI Gateway → pgc-chatbot → Guardrails
  • Point out which categories are set to Block (e.g. Violent Crimes, Indiscriminate Weapons) vs. Flag (logged for review, not blocked)
  • "Categories are tuned per business — a coffee shop's own knowledge base legitimately discusses pricing and payments, so overly aggressive blocking would create false positives. This is dialed in specifically for this use case."

Data Loss Prevention (DLP)

Dashboard ~1 min

Scanning for sensitive data patterns — PII, financial information — before it flows through the Gateway.

Capability: DLP scanning against predefined data-pattern profiles (financial information, identifiers, etc.), independent of Guardrails' content-safety scanning.
AI Gateway → pgc-chatbot → Settings → DLP
  • DLP scanning is enabled on this gateway
  • "This is a separate layer from Guardrails — Guardrails looks for unsafe intent, DLP looks for sensitive data patterns like card numbers or ID numbers leaking through a conversation. Specific detection profiles get added here as a business's compliance needs are defined."

Governance: Spend Limits & Rate Limiting

Dashboard ~1 min

Hard ceilings that protect budget and infrastructure, enforced by the Gateway itself — no app-side bookkeeping.

Capability: Spend Limits (hard daily cost ceiling) and Rate Limiting (requests-per-minute cap), both enforced before a request is even forwarded to a model provider.
AI Gateway → pgc-chatbot → Settings
  • Spend Limits — a hard daily cost ceiling; once hit, requests stop being forwarded to paid providers, protecting against a runaway bug or an abuse spike blowing the budget
  • Rate Limiting — caps requests per minute at the gateway level, independent of anything the app itself enforces
  • Authentication — the gateway itself requires a token on every call; only this app can use it

Custom Tooling on Gateway APIs

Dashboard ~2 min

Capability: the Gateway's Logs/Analytics REST API, used here to power a completely custom internal admin panel (/insights) — a proof that the platform's data isn't locked inside the native dashboard.
While already logged into /insights, point out
  • Live cards: total requests, cache-hit rate, spend, average latency, model/provider split — all pulled from the same Logs API shown earlier, just summarized differently
  • Recent activity table — click "View" on any row for a clean transcript of that conversation, with the large system prompt/knowledge base filtered out so only the real back-and-forth shows
  • "This entire page is custom-built in a day on top of the Gateway's own API — it's not a Cloudflare product. Whatever internal view a team actually wants, the data is there to build it."

Human Feedback Loop

Mention only ~30 sec

A capability worth mentioning even without a live click-through.

Capability: patchLog — any application can attach a rating (or other outcome data) to a specific logged request after the fact, visible and filterable in the native Logs UI.
Not demoed live: a thumbs up/down control existed in the chat UI earlier in this build and was removed to keep the customer-facing interface clean and free of extra clutter. The underlying capability (attaching feedback to a specific log entry via the Gateway's API) is still fully functional and can be re-surfaced — in the chat UI, a support tool, or anywhere else — whenever it's wanted.
